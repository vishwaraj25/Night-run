# Night Run — privacy and security

Written to be checkable, not reassuring. Every claim below points at the code
or the config that enforces it, so you can verify it rather than take my word,
and so can anyone you share the game with.

## What is collected

Two things, and nothing else:

1. **An anonymous player id.** A random UUIDv4 the game generates the first
   time it runs and keeps in its own save file (on the web, that is the
   browser's per-site storage, so it does not follow anyone across sites). It is not derived from your
   device, your OS, an account, an ad id, or anything about you — it is a
   random number. Clearing the game's data gives you a completely new one.
2. **Which in-game things happened.** Menu buttons clicked, run started,
   progress reached, item picked up, enemy defeated, checkpoint reached, boss
   defeated, run ended and why — plus, for some of those, a score, a duration,
   or an **x position in the level**.

That is the whole list; it is enumerated in `EVENT_SCHEMA` in
`backend/api/events.js` and mirrored in `ALLOWED_EVENTS` in
`game/autoload/telemetry.gd`. Anything not in it is refused by both.

That x is a coordinate in the game world. It is how you find out where players
give up. It is not a location on Earth and there is no code anywhere in this
project that asks for one.

## What is not collected

No name, no email, no account. No IP address. No user agent, device model, OS
version, screen size, or any other fingerprint. No location. No contacts, no
files, no other apps. No third-party analytics, ad SDK, or tracker of any kind
— the game has zero third-party dependencies at runtime.

**This is structural, not a policy.** There is no column in the database for
any of it (`backend/db/schema.sql`), and the API builds a fresh object from an
allow-list rather than storing what it was sent (`backend/api/events.js`), so
a modified client cannot cause personal data to be stored. There are tests for
exactly that:

```
backend/test/validation.test.js
  ✔ identifying fields cannot be smuggled in under any event
  ✔ an unknown payload key is REJECTED, not silently stored
  ✔ prototype pollution attempts are rejected

backend/test/integration.test.js     (real HTTP, database stubbed)
  ✔ what reaches Postgres is the id and allow-listed keys, nothing else
  ✔ a tampered client cannot smuggle a field into the database
  ✔ SQL injection in the ids is rejected before any query runs
  ✔ another site cannot post as the game
```

Run them with `cd backend && npm test`. 26 tests, all passing.

The integration suite is the one that backs the claim on this page: it asserts
on the exact parameters that would reach Postgres, not just on what the
validator returns.

## Telemetry is off by default

`Telemetry.enabled` is `false` (`game/autoload/telemetry.gd`). The shipped
build makes no network requests at all until someone deliberately turns it on
and points it at a real endpoint. If you never do, the game is entirely
offline.

## "Will this affect the device of someone I send it to?"

The web build is the safest way to share it, and it's the one to send people:

- Sound is generated by the game itself (18 synthesised effects, 304 KB) — no
  audio CDN, no third-party player, nothing fetched. **M** mutes it.
- It runs in the browser's sandbox. It cannot read files, reach other apps, or
  persist anything outside the browser's own per-site storage.
- The build requests **no permissions at all**. `build/web/_headers` sends a
  `Permissions-Policy` that explicitly denies geolocation, camera, microphone,
  USB, serial, bluetooth and motion sensors — so even if something in the page
  asked, a browser honouring the header refuses.
- A Content-Security-Policy restricts it to loading its own files. `connect-src
  'self'` means it cannot contact any server other than its own origin; to
  enable telemetry you add exactly one origin to that line, and nothing else
  becomes reachable.
- `X-Frame-Options: DENY` and `frame-ancestors 'none'` stop the game being
  embedded in someone else's page to fake a UI.

The Android APK is also sandboxed by Android itself, and requests **no
permissions** — not even internet, since telemetry is off
(`permissions/internet=false` in `game/export_presets.cfg`). You can confirm
that on the built file:

```bash
~/Library/Android/sdk/build-tools/34.0.0/aapt2 dump badging build/night-run.apk | grep permission
```

It prints nothing. That is the intended result.

One honest caveat: the APK is signed with a **debug key**, which is fine for
sending to people you know and sideloading, but it is not a release signature
and Android will warn on install. A public release needs a real upload key.

## Security of the telemetry endpoint

The endpoint is public and unauthenticated — anyone who finds the URL can post
to it. It is written on that assumption. The worst a hostile caller achieves is
inserting junk rows that look like real ones.

| Risk | What stops it |
|---|---|
| Arbitrary data stored | Per-event allow-list of keys **and** types; unknown key rejects the batch |
| SQL injection | Parameterised queries only; ids must match a UUIDv4 regex |
| Prototype pollution | Payload rebuilt with `Object.hasOwn` checks; tested |
| Any site posting as your game | CORS is an allow-list from `ALLOWED_ORIGINS`, never `*` |
| Flooding the database | Per-player-id rate limit, 30 requests/minute |
| Huge request bodies | 16 KB cap enforced **during** the read, not after |
| Man-in-the-middle on the DB | TLS with the certificate verified (`rejectUnauthorized: true`) |
| Error messages leaking internals | Fixed error strings; nothing from the request is echoed back |

Two of those were flaws in the first draft of this backend that I fixed rather
than shipped: it stored a `user_agent` (a device fingerprint), and it used
`rejectUnauthorized: false`, which is the usual copy-paste fix for managed-
Postgres certificate errors and also makes the connection impersonable.

## Deleting a player's data

The player id is the only key needed, and the game can show it
(`Telemetry.player_id`). One statement removes the person and every event they
ever sent:

```sql
DELETE FROM players WHERE player_id = '<uuid>';
```

`ON DELETE CASCADE` handles the events. In-game, `Telemetry.reset_identity()`
discards the id and mints a new one.

## Retention

Nothing here needs to live forever. `backend/db/schema.sql` includes the
statements to expire data past 180 days; run them on a schedule.

## Scope

This is one level behind a shareable link. Telemetry as described holds no
personal data, so it needs no consent banner in most jurisdictions — but that
is a judgement for you, and if you ever add anything identifying, this document
stops being accurate and would need rewriting rather than amending.

There is an Android APK in `build/` from earlier work. It is signed with a
debug key and is not part of the link you're sharing — sideload it to people
you know if you want, or ignore it.
